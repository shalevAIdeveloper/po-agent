# 0003 — Authentication and per-request authorization in the API

## Context
The web app signs users in with Supabase Auth (email + password; invite-only sign-up, invitations set the password). The FastAPI API must authenticate those users, decide which organization a request acts on, and keep RLS as a real second line of defense (ADR 0004) rather than something the API bypasses. Supabase now issues asymmetrically signed JWTs and publishes a JWKS; local Supabase (CLI 2.117) already signs with ES256.

## Decision
- **Token verification** (`app/auth/jwt.py`): signature checked against `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`. Only `ES256`/`RS256`; `HS*` and `none` are rejected before any key lookup, and the header `alg` must match the key. Required claims `exp`, `iat`, `sub`, `aud`, `iss`; `aud = authenticated`, `iss = ${SUPABASE_URL}/auth/v1`, 30 s leeway. Rejects `role ≠ authenticated` and anonymous sessions. JWKS is cached (10 min TTL); refetches (unknown `kid`, retries after a failure) happen at most every 30 s; if the endpoint is down, cached keys are trusted for at most 1 h past the TTL and then dropped, so a rotated-out key cannot live forever. The API holds no JWT secret. Outside local, `SUPABASE_URL` and `WEB_ORIGIN` must be `https` (a JWKS fetched over plain http could be swapped in transit).
- **Failures** return one generic `401 Not authenticated` with `WWW-Authenticate: Bearer`; the reason is logged as a fixed string, never the token. Auth not configured, or no usable signing keys → `503` (never open, and never a 401 that the web app would treat as a logout).
- **Claims passed to Postgres** (`request.jwt.claims`) are an allow-list of verified claims: `sub`, `role`, `aud`, `iss`, `iat`, `exp`, `aal`, `amr`, `session_id`, `is_anonymous`, `app_metadata`. **RLS policies and SQL functions may trust only `sub` (via `auth.uid()`), `role` and `app_metadata`** — never `user_metadata`, which users can edit and which is not forwarded.
- **Database role**: the API connects as `po_api` — `LOGIN NOINHERIT`, no BYPASSRLS, member only of `authenticated` with `SET` and without `INHERIT`. Every request runs in a READ COMMITTED transaction that does `set_config('role', 'authenticated', true)` and `set_config('request.jwt.claims', <verified claims>, true)` (`app/db.py: rls_transaction / run_as_user`), so RLS applies to API queries. A query that forgets to switch role fails with "permission denied" (fail closed); connecting as `postgres` (BYPASSRLS) would have failed open. Both settings are transaction-local, so nothing carries over on a pooled connection (pinned by an integration test with a pool of one). Role-level settings apply at login only, so `po_api` carries its own `statement_timeout = 8s` and `idle_in_transaction_session_timeout = 15s` (`authenticated`'s timeout does not apply after `SET ROLE`). Locally the password comes from `supabase/roles.sql` (local-only value); hosted projects set it out of band (0.5b).
- **Timeouts**: each API transaction sets `lock_timeout = 3s`; a statement (`57014`) or lock wait (`55P03`) timeout becomes `503 {"detail": "busy"}` with `Retry-After`, never a bare 500. **No external I/O (LLM, storage, HTTP) inside `run_as_user`**: the 15 s idle-in-transaction timeout would kill the connection; fetch first, then write in a short transaction.
- **Retries**: `run_as_user` retries the whole transaction on `40001` / `40P01` (max 3 attempts). Code that changes an org and its memberships in one transaction locks the org row first (same order as the last-owner trigger).
- **Active organization** (`app/auth/org.py: CurrentOrg`): `X-Org-Id` header; without it, a user's only org is used; several orgs without the header → `400`. Not a member (or no such org) → `404`, never `403`, so the API does not confirm another tenant's org exists. `require_role("owner", "admin")` → `403`. Membership is looked up per request (no custom JWT claims), so role changes apply immediately.
- **Errors from the DB** are mapped to stable codes (`slug_unavailable`, `organization_limit_reached`, `invalid_organization`); raw DB error text is never returned. Rate limiting is deferred to M7.
- **CORS** allows only `WEB_ORIGIN`.

## Consequences
- Key rotation needs no deploy; a leaked API config cannot mint tokens.
- Two independent isolation proofs: pgTAP on the DB, and integration tests with two real GoTrue users through the API as `po_api`.
- Tokens of a deleted or demoted user stay valid until they expire (`jwt_expiry` = 1 h); membership is re-checked per request, so a removed member loses org access immediately, but an authenticated session lingers. Revisit (shorter expiry / session checks) before pilot (M7).
- Hosted Supavisor connections use the user `po_api.<project-ref>` (0.5b).
