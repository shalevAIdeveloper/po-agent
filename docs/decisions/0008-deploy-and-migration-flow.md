# 0008 — Deploy and migration flow (Railway + Supabase)

## Context
0.5c deploys `web`, `api` and `worker` to Railway (environment `dev` now; `production` at pilot gate P1). Migrations already reach the hosted database through `migrate.yml` (0.5b). The two must not break each other, and nothing secret may travel with the code.

Railway's `railway.json` / `railway.toml` ("Config as Code") is deprecated: new services can't use it and existing files stop being read on 2026-12-01. Its replacement is Infrastructure as Code (`.railway/railway.ts`, `railway config plan` / `apply`).

## Decision
- **Images:** one Dockerfile per app, built by Railway from the repo (`apps/api` for `api` and `worker`, `apps/web` for `web`). Allow-list `.dockerignore`s: only `app/` + lockfiles for the API (no `tools/`, `tests/`, `evals/`, `.env*`; L4, A17), only sources and lockfiles for the web. Both run as non-root users (web code owned by root, read-only at runtime). Base images and the Dockerfile frontend (`# syntax=`) are pinned by digest (checked by `apps/api/tests/test_dockerfiles.py`), and pnpm by sha512 (corepack). The API image defaults to `APP_ENV=prod` (fail closed: every cloud setting required, https only, no docs, no `.env` files) and sets `PO_DEPLOYED=1`: inside the image, or wherever `RAILWAY_ENVIRONMENT_ID` is set, `APP_ENV=local` — or an empty value, which falls back to local — is a startup error. Railway sets `APP_ENV=dev` explicitly (`production` → `prod` at P1). The web build refuses a `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` that isn't `sb_publishable_…`. The API answers wrong trailing slashes with 404 instead of a redirect (`redirect_slashes=False`): behind the proxy it would point at `http://`.
- **One image, two services:** `worker` uses the API image with start command `python -m app.worker`. Until M1 it connects as `po_api` (same `DATABASE_URL`, as a Railway reference to the `api` variable, not a copy). The worker's own role comes with M1, when it has real work.
- **Infrastructure as Code:** `.railway/railway.ts` (TypeScript SDK `railway` pinned, typechecked in CI) declares the three services, region (same as Supabase), health checks (`/health`, web `/healthz`), restart policy and non-secret variables. Secrets are `preserve()` there and set by the owner in the dashboard; no Railway UUIDs or generated domains are committed. The file refuses any environment other than `dev` until P1. Changes are previewed with `railway config plan` and applied only after the owner approved that exact plan.
- **Deploy trigger:** after the first manual deploy, services track the `dev` branch with **`checkSuites` (wait for CI)**, so a push deploys only after `ci-ok` passed; watch patterns limit which paths redeploy which service. The CI `images` job builds both images and checks how they start before anything is merged. Turned on in PR #12, with what that gate depends on (`sec`): CI has no workflow-level path filter, so every push to `dev` has a CI suite to wait for; CI runs on `dev`/`main` are never cancelled (a cancelled run would skip that commit's deploy); Railway PR Environments and Bot PR Environments stay off (they would deploy unreviewed branches with `dev`'s variables); after autodeploy is on, `railway up` is not used and rollback is Redeploy; only the owner merges to `dev` (merge = deploy). The gate itself is verified on the first autodeploy (WAITING during CI, then SUCCESS; runbook §6).
- **Migrations vs. deploys (expand / contract):** `migrate.yml` and the Railway deploy both start on a push to `dev`. When that commit changes migrations, `migrate` is one of the check suites the deploy waits for, so a failed migration blocks the deploy; otherwise they are not ordered. So every migration must work with the code that is already running (expand: add tables/columns/functions, nullable or with defaults), and code that stops using something ships first; removing it (contract) is a later migration. No `preDeployCommand` migrations: the database is changed only by `migrate.yml`.
- **Database connection:** `po_api` through Supavisor **session mode** (IPv4) — Supabase's direct host is IPv6-only, and session mode keeps prepared statements safe (A2). **TLS verify-full outside local:** the API requires `DATABASE_CA_CERT` (the public Supabase CA, PEM, set as a Railway variable, never committed) and passes asyncpg an `SSLContext` that checks chain + hostname; TLS options in the URL (`ssl*`, any case, and `direct_tls`) are dropped, a weak `sslmode` (`disable`/`allow`/`prefer`, also %-encoded) is rejected at startup, and any other query parameter except `application_name` is rejected at startup (it would otherwise fail at the first query, after the health check passed). Without this asyncpg would default to `prefer`, which silently falls back to plain text.
- **Request ids and client IPs:** the API generates its own `request_id`; a caller's `x-request-id` is only logged as `client_request_id` (L7). Uvicorn trusts forwarded headers from localhost only: the API doesn't use client IPs. The web's rate limiter (A13) will be the first consumer of Railway's client-IP header and decides how to trust it.
- **What is public:** `/health` and `/healthz` return only `{"status":"ok"}` (L8); `/docs` and `/openapi.json` exist only locally (L5). The runtime image has no OpenTelemetry SDK, and `OTEL_SDK_DISABLED=true` (L6).

## Consequences
- A broken Dockerfile fails CI, not the dev deploy.
- A destructive schema change needs two PRs (expand, then contract).
- `production` at P1 = add its Supabase URL to `railway.ts`, create the Railway environment, re-run this runbook; nothing else changes.
- IaC is young (SDK README calls it beta): pin the SDK and CLI, and always read the plan.
